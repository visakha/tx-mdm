# Bare-bones step-driver package — all sources (v2.1 "why-not" variant)

Bare-bones variant of `Snowflake_All_Sources_Modular_Step_Driver_v2.1`:
the same driver / step / publish / runner structure, with all logging,
auditing, and control-plane code removed. No config table, no
checkpoints, no job-run id, no input-table checks. The driver still
returns one big summary string — that string is the only output.

## What was removed (exact list)

- `COMMON.ETL_RUN_CONFIG_TBL` and everything that read it: the GATHER
  block, the Y/N flags, the driver-row gate, and all seed files.
  There are no seed files in this package.
- All checkpointing: `sp_etl_checkpoint`, `sp_etl_job_begin`,
  `sp_etl_job_finish`, `sp_etl_job_fail`, and the job-control DDL
  (`01_job_control_ddl.sql`), job-control procs
  (`02_job_control_procs.sql`), and config DDL
  (`03_etl_run_config_ddl.sql`) are gone entirely.
- `P_JOB_RUN_ID`, `P_INPUT_TABLES`, `l_job_run_id`, `l_flag_*`,
  `l_in_*`, `l_pub_*` — none of these exist anywhere in code.
- The INFORMATION_SCHEMA existence checks and EXECUTE IMMEDIATE probe
  blocks in step and publish procs.
- Config/job-control documentation. There is no COMMON schema in this
  package at all.

## What was kept, and why

- The structure: one driver per mapping, one proc per transform step,
  one proc per publish INSERT, one runner per workflow. Drivers keep
  their original parameters only (no `P_JOB_RUN_ID`).
- Step 5: bare `DROP TABLE IF EXISTS` cleanup, unchanged.
- `l_run_ts`: still generated by each driver, because step SQL uses it.
- ONE publish transaction per driver: `BEGIN` → branch calls in
  order → `COMMIT`; on exception `ROLLBACK` + `RAISE`. No checkpoint,
  no job-fail call.
- The summary: each step and branch returns its row count; the driver
  formats each count into `l_summary` with `fn_snow_helper36_common`
  (same labels and order as v2.1) and `RETURN`s the big string. Each
  runner calls its drivers with zero arguments, concatenates their
  returned strings with a per-mapping header line, and `RETURN`s the
  combined string.
- The common helpers, verbatim: `00_common/01_snow_common_functions.sql`
  and `00_common/02_snow_common_lookups.sql` (business functions, not
  logging). `fn_snow_helper36_common` is what formats the summary.
- Business SQL verbatim: every step CTAS and publish INSERT is
  identical to v2.1 except for the removals above.

## "No counts" — what it means, precisely

Row counts appear ONLY inside the returned summary string. Steps and
branches still RETURN their counts (the summary needs them), drivers
format them into `l_summary`, runners concatenate. NOTHING is written
to any table — no checkpoint rows, no metrics, no audit tables. If you
do not capture the returned string, the counts are gone.

## Structure and counts

- `00_common/` — the two helper files (shared by all sources).
- One folder per source: `drivers/`, `steps/`, `publish/`,
  `manifests/` (slim, no Mermaid diagrams), `runners/`.
- TRS: 15 drivers, 66 steps, 38 branches. ECI: 9, 32, 26. WIC: 5, 17,
  19. TTF: 4, 12, 13. FSS: 6, 21, 23. CRE: 1, 5, 18.
- Totals: 40 drivers, 153 steps, 137 publish branches, 40 manifests,
  7 runner procs + 7 run scripts.
- `DEPENDENCIES.md` — work-table producer/consumer chains per mapping
  (no config columns). `STEP_MAP.md` — step maps for all 40 mappings.
  `STRIPPED_NOTES.md` — the exact removal list with before/after
  notes per proc kind, plus the run command.

## Install rule

Install EVERYTHING for one source — its drivers, steps, publish
procs, AND both helper files — into ONE schema, because drivers call
helpers unqualified. A second schema holding only helpers does not
work unless callers qualify the names (they do not). The RDM reference
data for the lookups is separate: the seven reference objects still
need real definitions before a production install —
`V_LOOKUP_CODE_VALUE`, `REF_JUNK_NAME_LIST`, `REF_MATCHCODE_DESC`,
`RDM.REF_PHN_AREA_CD`, `EXC_LOOKUP_CODE_VALUE`, `LOOKUP_CODE_VALUE`,
`REF_DYLGHT_SVNGS_TM` (same list as v2.1 COMPILE_NOTES; lookup UDFs
are unchanged and no stubs are shipped).

## How to run (Windows)

From Windows Command Prompt (`cmd`; PowerShell also accepts `>`
redirection), calling the TTF workflow runner and logging its
returned summary string to a file:

```
snowsql -a DOOPELI-LL99227 -u VIZY --authenticator SNOWFLAKE_JWT --private-key-path C:\keys\vizy_rsa_key.p8 -r ACCOUNTADMIN -w SNOWFLAKE_LEARNING_WH -d MDM_ETL_TTF -s TTF_ETL_WRK -q "CALL sp_etl_run_wf_TTF_Stage_Load();" > C:\logs\ttf_stage_load.log 2>&1
```

- The private key file must be a copy on the Windows machine (the
  compile machine's copy is not reachable from Windows); the key is
  unencrypted so no passphrase is needed.
- `-d` / `-s` / `-w` are the install database / schema / warehouse —
  adjust to the actual install (the example uses the package's
  documented TTF topology).
- The runner takes no arguments and RETURNs the combined summary
  string; snowsql prints the result and `>` captures it into the log
  file (optionally add `-o output_format=csv -o header=False` for a
  bare value instead of the formatted table, if the installed snowsql
  version accepts those options).
- Flag names verified against Snowflake's snowsql docs
  (`-a` / `-u` / `-d` / `-s` / `-w` / `-q` / `-o` /
  `--private-key-path` / `--authenticator SNOWFLAKE_JWT`).

## Notes and judgement calls

- TRS party-deactivation step 50 (`DELETE_VALID_STAGE_NOT_PERFORMED`)
  had no business SQL — its only action was a checkpoint. It is kept
  as a proc that just `RETURN`s 0, still called after the publish
  transaction, so the 66-step count and the summary line are
  preserved.
- Branch summary appends sit immediately after each branch call
  inside the publish transaction (string concatenation only, no SQL
  side effects), reusing `l_rows`. This is the uniform pattern across
  all six sources; the returned summary string is unchanged in
  content and order versus v2.1.
- Runner zero-argument calls are behaviour-identical to v2.1: v2.1
  runners passed only `P_JOB_RUN_ID` (now removed as a parameter),
  and original params already took their defaults in v2.1 runs.
  Runner errors propagate (drivers roll back their own publish
  transactions; runners own no transaction).
- `P_RUN_TS` is kept in every step signature (steps use it in their
  CTAS, or carry it unused per the uniform rule). Publish branches
  keep `P_RUN_TS` only where the INSERT references `:P_RUN_TS`
  directly: TRS 27 of 38, WIC 1 of 19 (ALT), TTF 1 of 13 (ALT), FSS 1
  of 23 (ALT), ECI 0 of 26, CRE 0 of 18. A `run_ts` column read from a
  step table does not count.
- Where an original param carries a DEFAULT before `P_RUN_TS`, the
  step gives `P_RUN_TS` DEFAULT NULL too (Snowflake forbids
  required-after-optional; drivers pass positionally, so behaviour is
  unchanged). No step SQL anywhere referenced `P_JOB_RUN_ID`.

## What is NOT validated

No live Snowflake compile, run, or row-count parity was performed for
this package (same standing caveat as v2.1). Static verification only:
counts reconcile with v2.1; business SQL strip-and-compare per source;
banned-identifier grep returns zero code-line hits; every call site
arity-checked against its callee's new signature; every driver
`RETURN`s `l_summary`; every runner `RETURN`s a concatenated string.
Compile-time items still to confirm on first run: the scalar-call
capture form `l_rows := (CALL proc(...));`, zero-argument calls to
drivers with defaulted params, and the empty-transaction path (all
branches skipped — impossible here, since there are no flags: every
branch always runs).
